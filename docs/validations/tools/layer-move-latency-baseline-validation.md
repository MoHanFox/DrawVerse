## 结论和下一阶段候选

**已证实行为**：第一次按下的同步调用约0.08–0.15ms，无资产时同步调用不等待准备完成；异步BEGIN完成仍需等待观察，已准备常驻段甚至可观察到约73–114ms起始区间；成功Move p95通常约0.032–0.050ms。即时拖动实际走CPU；准备完成的兼容S1–S3走常驻同源四顶点，固定有效未链接蒙版S4回退CPU。单条历史、终值、撤销重做和取消恢复已在成功运行及专项验证。没有据此宣称资源准备对所有机器/真实场景无影响。

**有测量支持的重点区间**：成功4K松手→GUI元数据通常约17–33ms，→完整视口接收约0.36–0.80s；S1约0.05–0.06s。Qt worker读帧尝试p95通常约0.3–0.6ms，常驻拖动并未反复创建纹理，不能把数百毫秒都归咎于Qt纹理上传。代码核对：关闭后恢复普通renderer任务；拖动CPU路径render_interactive，常驻时不发相同CPU帧任务。相关性支持优先检查关闭后的正常帧任务/发布链，**不能据当前记录证明CPU计算独占了全部等待**。

**尚未验证的假设**：CPU池排队、普通合成执行、旧job结束/替换、floor/request选择各贡献多少；两次意外CANCEL的具体入口；首次驱动/磁盘冷页、实体鼠标手感、真实学生层栈、真实屏幕显示延迟。未清OS缓存，未切GPU，没有学生资源或数位板数据；本轮不是这些环境的替代验收。

最多两个候选，均未实施：

1. **优先：拆清松手后的完整视口任务排队→执行→发布→接收区间**，按已有generation/request/revision补最小核心任务观测，再判断是否有多余重建或过时任务等待。原因是稳定的数百毫秒收尾明显大于同步输入及Qt读帧调用，覆盖S2/S3/S4，而常驻源复用已实际成立。
2. 拆清已准备常驻首操作的约73–114ms BEGIN回执/GUI心跳间隔，核对核心完成时刻与GUI/render同步边界；没有证据前不调16ms合并或预热策略。两次CANCEL及像素专项偶发失败也必须保留有限生命周期记录来排除干扰，不能写成学生卡顿根因。
